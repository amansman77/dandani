# 신뢰 가능한 테스트 환경 구축

## Problem 1-Pager

### Context

루트 품질 검사는 lint, Worker 정적 검사, 단위 테스트, 빌드와 Worker 번들 검사를 CI에서
실행한다. 하지만 테스트는 UTM 파서와 일부 날짜 유틸리티만 다루며 현재 제품의 문장 API와
사용자 흐름을 보호하지 못한다.

### Problem

문장 시작, 조회, 되새기기, 은퇴의 회귀가 생겨도 현재 CI가 성공할 수 있다. 기존 Playwright
자동화도 운영 사이트를 관찰해 로그만 남기므로 결정적 테스트나 배포 게이트가 아니다.

### Goal

- 활성 문장 API의 성공·실패·중복 요청을 결정적으로 검증한다.
- 핵심 화면의 사용자 상호작용을 브라우저 API 수준에서 검증한다.
- 단언형 E2E와 커버리지 기준을 CI가 실행하도록 만든다.
- 로컬과 CI의 Node 버전 기준을 일치시킨다.

### Non-Goals

- 레거시 challenge, practice, story API를 다시 테스트 대상에 포함하지 않는다.
- 실제 운영 D1 데이터나 Discord, 분석 서비스에 테스트 요청을 보내지 않는다.
- 이번 작업에서 모든 파일의 높은 커버리지를 달성하지 않는다.

### Constraints

- 테스트는 외부 네트워크와 시간에 의존하지 않아야 한다.
- 비밀 값과 실제 사용자 데이터를 사용하지 않는다.
- 테스트용 fake가 지원하는 SQL 범위를 명시하고 실제 D1 검증을 대체한다고 주장하지 않는다.

## 선택지 비교

1. Miniflare와 로컬 D1: 운영 유사성이 높지만 설정과 의존성, 마이그레이션 실행 비용이 크다.
2. 문장 API 전용 in-memory D1 fake: 빠르고 결정적이지만 SQLite 문법·제약 자체는 검증하지 않는다.

우선 2번으로 라우터와 서비스 계약을 고정한다. 이후 로컬 D1 계약 테스트를 별도 계층으로
추가하며, fake 테스트를 실제 D1 검증으로 오해하지 않도록 테스트 지원 코드에 범위를 적는다.

## 구현 순서

1. 문장 API 라우터 통합 테스트와 전용 D1 fake
2. 온보딩·문장 시작·되새기기 핵심 UI 테스트
3. 로컬/프리뷰 대상 단언형 Playwright 스모크 테스트
4. 변경 범위 중심의 커버리지 기준과 CI 연결
5. Node 버전 기준 통일 및 테스트 문서 갱신
