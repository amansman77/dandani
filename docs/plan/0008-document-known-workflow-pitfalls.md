# Problem 1-Pager: 작업 중 혼란과 대응 방법 문서화

## Context

프로젝트 컨텍스트 정리와 배포 과정에서 제품의 현재/레거시 경계, worktree 권한,
설치되지 않은 의존성, 배포 대상의 차이, 오래된 검증 명령 때문에 여러 번 판단이 필요했다.

## Problem

이 정보가 실행 로그에만 남으면 다음 작업자가 같은 실패를 반복하거나, 기능 브랜치에서
의도하지 않게 프로덕션 Worker를 배포할 수 있다.

## Goal

- 실제로 겪은 혼란을 증상, 원인, 다음 행동 형식으로 기록한다.
- 다음 작업 전 확인할 수 있도록 에이전트와 배포 문서에서 연결한다.
- 배포 가이드의 레거시 API 검증 예시를 현재 API로 수정한다.

## Non-Goals

- 의존성 업그레이드 또는 보안 취약점 자동 수정
- 배포 자동화나 권한 정책 변경
- 레거시 코드 및 과거 문서 삭제

## Constraints

- 비밀값, 로컬 사용자 정보, 인증 토큰을 문서에 기록하지 않는다.
- 특정 실행 환경의 현상을 프로젝트의 보편적 사실처럼 단정하지 않는다.
- 실제 배포에서 확인한 Cloudflare Pages와 Workers의 대상 차이를 명시한다.

## Options

1. 기존 문서 각 위치에 주의사항을 분산한다: 문맥에는 가깝지만 발견과 갱신이 어렵다.
2. 알려진 혼란을 전용 문서에 모으고 관련 진입점에서 연결한다: 문서가 하나 늘지만 재사용과
   사전 점검이 쉽다.

**Decision:** 2번을 선택하고, 잘못된 배포 검증 명령은 원래 위치에서도 바로잡는다.

## Assumptions

- 이 문서는 2026-09-12 작업에서 관찰한 사실을 기준으로 하며 환경이 바뀌면 갱신한다.
- 기능 브랜치의 Pages 직접 배포는 브랜치 배포이고 Worker 직접 배포는 공유 Worker 갱신이다.
